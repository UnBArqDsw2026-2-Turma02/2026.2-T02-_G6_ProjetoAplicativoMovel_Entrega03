### GoF Comportamental
#### Contexto (Problema)
No aplicativo da CNH, quando o condutor pede para alterar a categoria da habilitação, o sistema precisa checar várias regras antes de aceitar. Na Entrega 1, observando o aplicativo, vimos duas delas: as opções são filtradas pela categoria atual do condutor, e as categorias C, D e E não são tratadas no aplicativo (ele manda procurar o Detran da UF).

**Sem o padrão**, todas essas regras ficariam em um método só, `validar_elegibilidade`, dentro da solicitação, num bloco de `if/elif`. Cada regra nova obrigaria a mexer nesse mesmo método, e a ordem das checagens ficaria escondida no meio do código.

**Com o padrão**, cada regra vira uma classe validadora. A solicitação só entrega o pedido ao primeiro validador, e cada um decide se resolve ou se passa adiante. O livro descreve o padrão assim: dar a mais de um objeto a chance de tratar o pedido, encadeando os receptores até que um trate (GAMMA et al., 2000). O Refactoring Guru acrescenta que ele serve quando a ordem dos tratadores importa e quando o conjunto deles pode mudar em tempo de execução (REFACTORING GURU, 2026).

**O que foi observado e o que é decisão nossa**

| Regra | Origem |
|---|---|
| C, D e E vão para o Detran | Observado na Entrega 1 (tela de alteração de categoria e BPMN) |
| Para quem tem B, o aplicativo ofereceu só ACC+B e AB | Observado na Entrega 1 |
| Opções para quem tem A ou ACC | Texto "Como funciona" do aplicativo; **não testadas** |
| Bloqueio ativo impede a alteração | **Decisão de projeto.** Só vimos a tela "Não existem bloqueios ativos" |
| Ordem dos validadores | **Decisão de projeto** |

**Elo com a Entrega 2.** O Diagrama de Classes tinha `SolicitacaoAlteracaoCategoria.validarElegibilidade(): boolean` e `OrgaoDeTransito.encaminharAtendimentoPresencial()`, e o Diagrama de Sequência usava um `alt` para a decisão C/D/E. Aqui a mesma decisão vira uma cadeia de objetos. Uma mudança consciente: `validar_elegibilidade` agora devolve **três** resultados (aceita, recusada, encaminhada ao Detran) e não mais um `boolean`, porque "encaminhada" não é nem aceitar nem recusar.

**Papéis do padrão no nosso projeto**

| Papel GoF | Classe | Arquivo | Origem |
|---|---|---|---|
| Handler | `Validador` | `validador.py` | Decisão de projeto |
| ConcreteHandler 1 | `ValidadorDetran` | `validador_detran.py` | Observado na Entrega 1; gateway do BPMN; `alt` do Diagrama de Sequência (Entrega 2) |
| ConcreteHandler 2 | `ValidadorCompatibilidade` | `validador_compatibilidade.py` | Observado na Entrega 1 (para B); A e ACC pelo texto do aplicativo |
| ConcreteHandler 3 | `ValidadorBloqueios` | `validador_bloqueios.py` | Decisão de projeto; usa `possui_bloqueio_ativo()` do Diagrama de Classes da Entrega 2 |

O diagrama mostra duas partes:

#### Implementação (Código & Vídeo com Padrão em Execução)
Código: [codigo/chain_of_responsibility](https://github.com/UnBArqDsw2026-2-Turma02/2026.2-T02-_G6_ProjetoAplicativoMovel_Entrega03/tree/main/docs/Base/Relatorios/SubEquipe_03/codigo/chain_of_responsibility). Para rodar, dentro da pasta: `python main.py` (demonstração) e `python -m unittest -v` (testes). Todos os dados são fictícios.

**Handler: `Validador`**

```python
class Validador:
    def __init__(self):
        self.proximo = None

    def definir_proximo(self, proximo):
        self.proximo = proximo
        return proximo  # devolve o próximo para dar para encadear numa linha só

    def validar(self, solicitacao):
        resultado = self.tratar(solicitacao)
        if resultado is not None:
            return resultado
        if self.proximo is not None:
            return self.proximo.validar(solicitacao)
        return ACEITA  # chegou ao fim da cadeia sem ninguém barrar

    def tratar(self, solicitacao):
        raise NotImplementedError("cada validador implementa o seu tratar()")
```

É o coração do padrão. O `validar()` faz a cadeia andar: chama o `tratar()` do próprio validador e, se ele devolver `None` (não resolvi), passa a solicitação para o próximo. Se não houver próximo, ninguém barrou e o resultado é `ACEITA`. É a minha forma de evitar o risco do pedido chegar ao fim sem ser tratado.

**ConcreteHandler 1: `ValidadorDetran`**

```python
class ValidadorDetran(Validador):
    def __init__(self, orgao):
        super().__init__()
        self.orgao = orgao

    def tratar(self, solicitacao):
        if solicitacao.categoria_desejada in ["C", "D", "E"]:
            solicitacao.motivo = self.orgao.encaminhar_atendimento_presencial()
            return ENCAMINHADA_AO_DETRAN
        return None
```

Para C, D e E ele resolve: registra o motivo usando o `OrgaoDeTransito` e a cadeia **para**. Nas outras categorias devolve `None` e passa adiante.

**ConcreteHandler 2: `ValidadorCompatibilidade`**

```python
OPCOES = {
    "B": ["ACC+B", "AB"],
    "A": ["AB"],
    "ACC": ["A", "AB", "ACC+B"],
}

class ValidadorCompatibilidade(Validador):
    def tratar(self, solicitacao):
        atual = solicitacao.habilitacao.categoria
        permitidas = OPCOES.get(atual, [])
        if solicitacao.categoria_desejada not in permitidas:
            solicitacao.motivo = ("A categoria " + solicitacao.categoria_desejada
                                  + " não está disponível para quem tem " + atual + ".")
            return RECUSADA
        return None
```

Confere se a categoria pedida está entre as opções para a categoria atual. Só a linha do `B` foi observada no aplicativo; as de `A` e `ACC` vêm do texto "Como funciona" da tela e não foram testadas.

**ConcreteHandler 3: `ValidadorBloqueios`**

```python
class ValidadorBloqueios(Validador):
    def tratar(self, solicitacao):
        if solicitacao.habilitacao.possui_bloqueio_ativo():
            motivos = ", ".join(solicitacao.habilitacao.bloqueios_ativos)
            solicitacao.motivo = "Habilitação com bloqueio ativo: " + motivos + "."
            return RECUSADA
        return None
```

Recusa se a habilitação tiver bloqueio ativo. É decisão de projeto (ver a tabela do contexto).

**Client: `SolicitacaoAlteracaoCategoria`**

```python
def validar_elegibilidade(self, primeiro_validador):
    resultado = primeiro_validador.validar(self)
    self.status = resultado
    return resultado
```

A solicitação só conhece o **primeiro** validador. Não sabe quantos existem nem em que ordem, que é a vantagem do padrão.

**Montagem da cadeia (`main.py`)**

```python
def montar_cadeia(orgao):
    primeiro = ValidadorDetran(orgao)
    primeiro.definir_proximo(ValidadorCompatibilidade()).definir_proximo(ValidadorBloqueios())
    return primeiro
```

A ordem é Detran, compatibilidade e bloqueios. Colocar o Detran primeiro é uma escolha: se o condutor pedir C, D ou E, ele é encaminhado mesmo que tenha bloqueio.

#### Senso crítico
- **Quando não usar.** Com poucas regras, fixas e simples, um `if/elif` basta e é mais fácil de ler. A cadeia compensa quando as regras tendem a crescer ou mudar de ordem.
- **Alternativa considerada: Strategy.** O Strategy escolhe **uma** regra conforme o contexto. Aqui precisamos aplicar **várias** verificações em sequência, parando na primeira que resolve, então o Chain of Responsibility se encaixa melhor.
- **O pedido pode não ser tratado.** O livro aponta que, sem receptor explícito, o pedido pode chegar ao fim da cadeia sem tratamento (GAMMA et al., 2000). Nós tratamos isso com o `ACEITA` no fim. Isso é uma escolha de projeto: se esquecermos uma regra, o pedido passa em vez de ser barrado.
- **A ordem importa e é fácil de errar.** O teste de ordem mostra que trocar a posição muda a mensagem ao usuário. Esse é o custo de espalhar a lógica em vários objetos: para entender o resultado é preciso seguir a cadeia inteira.
- **Limites do que fizemos.** As regras de `A` e `ACC` não foram observadas, a regra de bloqueios é decisão nossa, e os dados do código são fictícios.

#### Comparação com outros padrões comportamentais
Estes padrões também lidam com "quem faz o quê quando um pedido chega", mas respondem a perguntas diferentes (GAMMA et al., 2000):

| Padrão | Ideia | Diferença para o Chain of Responsibility no nosso caso |
|---|---|---|
| Strategy | Troca o algoritmo usado, escolhendo uma entre várias estratégias | Aqui não escolhemos uma regra: aplicamos várias em sequência e paramos na primeira que resolve |
| Command | Transforma o pedido em um objeto | Poderia representar a solicitação, mas não decide quem a trata. Os dois podem andar juntos |
| Observer | Avisa vários interessados quando algo muda | No Observer todos os interessados são avisados. Na cadeia, o pedido para no primeiro validador que resolve |
| State | O comportamento do objeto muda conforme o estado dele | O State decide o que a habilitação pode fazer em cada estado. A cadeia valida um pedido de alteração antes de ele ser aplicado |

State e Observer são os outros dois padrões escolhidos pela equipe, e os três giram em torno da `Habilitacao`: o estado em que ela está (State), quem acompanha as mudanças dela (Observer) e se um pedido de alteração é aceito (Chain of Responsibility).
