# Projeto Geral — MVP da SubEquipe_01

> Entrega adicional da SubEquipe_01: um pequeno sistema que junta, numa mesma aplicação, os três GoFs criacionais da equipe.

## O que é

Na entrega principal, cada integrante aplicou um padrão criacional a um caso de uso diferente do fluxo de veículos. O **Projeto Geral** reúne esses padrões num único MVP (produto mínimo viável) com telas simples. Uma pessoa escolhe um veículo, consulta as pendências, atualiza o endereço e emite o CRLV-e.

Os padrões continuam com os mesmos participantes da entrega principal. A diferença é que agora eles trabalham juntos, sobre os mesmos dados.

> Os dados são simulados. O MVP é uma proposta acadêmica e não representa o sistema real do DETRAN-DF Digital.

## Parte de cada integrante

| Integrante | Padrão | Parte no MVP | Código | Tela |
|--|--|--|--|--|
| Edson Pereira | Factory Method | Consultas de débitos, restrições, financiamentos e nada consta. O "Nada Consta" também é a validação usada antes de emitir o CRLV-e | `padroes/consultas.py` | Consultas |
| Ricardo Henrique | Factory Method + Multiton | Base de dados única por UF, compartilhada por todo o sistema, e os serviços do DETRAN (alteração de endereço e emissão) | `nucleo/base_detran.py`, `padroes/servicos.py` | Endereço |
| Yuri Andrade | Prototype | Emissão do CRLV-e por clonagem de um documento-base | `padroes/documentos.py` | CRLV-e |

A integração (servidor, telas e camada de aplicação) foi feita sobre essas três partes.

## Como funciona

```text
Escolher UF e veículo  →  Consultar pendências  →  Atualizar endereço  →  Emitir CRLV-e
     (Multiton)            (Factory Method)      (Factory Method)       (Factory Method + Prototype)
```

1. **Base única (Multiton):** cada UF tem uma única base de veículos. Todas as telas usam a mesma instância, então o que muda em uma tela aparece nas outras.
2. **Consultas (Factory Method):** cada consulta é criada pelo seu Creator (`DebitosCreator`, `RestricoesCreator`, `FinanciamentosCreator`, `NadaConstaCreator`).
3. **Alteração de endereço (Factory Method):** o `AlteracaoEnderecoCreator` cria o serviço, que aplica as regras do UC03 e grava o novo endereço na base.
4. **Emissão do CRLV-e (os três padrões juntos):**
   - o `EmissaoCRLVeCreator` cria o serviço de emissão;
   - o serviço consulta o **Nada Consta**;
   - sem pendências, o `EmissorCRLVe` **clona** o CRLV-e base e preenche placa, RENAVAM e exercício;
   - com pendências, a emissão é recusada e nenhum documento é criado.

Cada ação mostra uma **notificação** na tela: sucesso, aviso ou erro.

## Telas

| Tela | O que mostra |
|--|--|
| Início | Escolha da UF e do veículo e a situação dele |
| Consultas | Um card para cada consulta e o próximo passo sugerido |
| Endereço | Formulário de novo endereço e o resultado da validação |
| CRLV-e | Emissão do documento e a prova de que cada documento é um objeto novo, enquanto o documento-base continua vazio |
| Padrões | Os participantes de cada padrão e o fluxo da emissão |

## Como executar

É preciso ter Python 3.10 ou superior instalado. Não há bibliotecas para instalar.

```bash
cd docs/Base/Relatorios/SubEquipe_01/Projeto_Geral
python server.py
```

Depois, abra **http://localhost:8000** no navegador.

Veículos para testar:

| Placa | O que acontece |
|--|--|
| JKA1234 (DF) | Sem pendências: altera o endereço e emite o CRLV-e |
| ABC1D23 (DF) | Débitos e restrição: alteração e emissão bloqueadas |
| XYZ9A87 (DF) | Financiamento: altera o endereço, mas não emite o CRLV-e |
| GOA1B23 (GO) | Veículo da base de Goiás, outra instância do Multiton |
