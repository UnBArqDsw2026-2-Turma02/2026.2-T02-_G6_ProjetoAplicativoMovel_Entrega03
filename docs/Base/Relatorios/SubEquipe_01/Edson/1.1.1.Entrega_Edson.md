### GoF Criacional
#### Contexto (Problema)

No aplicativo do Detran-DF, o usuário informa a placa e o Renavam do veículo para consultar débitos, restrições, financiamentos ou emitir o "nada consta". Ao analisar o fluxo do aplicativo, percebe-se que todas as quatro opções partem da mesma tela inicial e entregam um retorno direto ao usuário. No entanto, embora a interface precise lidar com essas consultas de forma uniforme, pelo comportamento observado, infere-se que cada uma delas é implementada de maneira diferente no sistema. Sem um padrão o cliente escolheria qual consulta instanciar utilizando uma estrutura condicional:

```python
if tipo == "debitos":
    consulta = ConsultaDebitos()
elif tipo == "restricoes":
    consulta = ConsultaRestricoes()
elif tipo == "financiamentos":
    consulta = ConsultaFinanciamentos()
```

Contudo essa abordagem é problemática, visto que causa:
   * Acoplamento: o cliente conhece todas as classes concretas.
   * Violação do Open/Closed: cada novo tipo (por exemplo, “consulta de multas”) obriga a editar o cliente.
   * Duplicação: o mesmo if/elif tende a se repetir em cada tela ou fluxo que faz consultas.

Aqui entra o Factory Method:
  O padrão move a decisão de qual consulta criar para subclasses de um Creator. O cliente passa a depender apenas da abstração Consulta, e incluir um novo tipo significa adicionar duas classes (o produto e o seu creator), sem alterar o código existente.

O diagrama de sequência (Figura 1) ilustra a consulta de **débitos**, escolhida como exemplo. O fluxo ocorre da seguinte forma:

1. O usuário informa o Renavam e escolhe o tipo de consulta no aplicativo, e o **cliente** aciona o `DebitosCreator` por meio do método `consultar(renavam)`.
2. O `DebitosCreator` chama o seu próprio `criar_consulta()` (o Factory Method), que instancia a `ConsultaDebitos`. Esse é o único ponto em que a classe concreta é conhecida.
3. O Creator executa a consulta criada com `executar(renavam)`, e a `ConsultaDebitos` busca os dados na `BaseDetran`.
4. O `ResultadoConsulta` retorna ao Creator, depois ao cliente, e é exibido ao usuário.

O ponto central do diagrama é que o cliente interage **apenas com o Creator** e nunca instancia nem referencia a classe concreta da consulta. Para os demais tipos (restrições, financiamentos e nada consta), o fluxo é idêntico, mudando apenas o Creator acionado e o produto criado.

O diagrama de classes (Figura 2) apresenta os quatro participantes do padrão, identificados pelos estereótipos:

* **Product (`Consulta`):** classe abstrata que define a interface comum `executar(renavam)`, a mesma para todos os tipos de consulta.
* **Concrete Products (`ConsultaDebitos`, `ConsultaRestricoes`, `ConsultaFinanciamentos` e `ConsultaNadaConsta`):** herdam de `Consulta` e implementam `executar` de acordo com a fonte de dados de cada tipo.
* **Creator (`ConsultaCreator`):** classe abstrata que declara o Factory Method `criar_consulta()` e implementa o método `consultar(renavam)`, o qual usa o produto criado sem conhecer a sua classe concreta.
* **Concrete Creators (`DebitosCreator`, `RestricoesCreator`, `FinanciamentosCreator` e `NadaConstaCreator`):** sobrescrevem `criar_consulta()` e decidem qual `Consulta` concreta instanciar.

Há ainda duas classes de apoio, que não fazem parte do padrão: `ResultadoConsulta`, que padroniza o retorno das consultas, e `BaseDetran`, que simula as fontes de dados do sistema. As relações de herança ligam cada produto concreto à `Consulta` e cada creator concreto ao `ConsultaCreator`, enquanto a dependência de criação (`<<creates>>`) liga cada Concrete Creator ao seu produto. Dessa forma, incluir um novo tipo de consulta, como a de multas, exige apenas adicionar um novo par produto-creator, sem alterar as classes existentes, o que atende ao princípio Open/Closed.


#### Implementação (Código & Vídeo com Padrão em Execução)

O padrão foi implementado em Python, no arquivo [`app.py`](https://github.com/UnBArqDsw2026-2-Turma02/2026.2-T02-_G6_ProjetoAplicativoMovel_Entrega03/blob/feature/subequipe-1/docs/Base/Relatorios/SubEquipe_01/app.py). O código abaixo corresponde ao Factory Method aplicado à consulta veicular e segue o diagrama de classes da Figura 2.

```python

from abc import ABC, abstractmethod
from dataclasses import dataclass, field

class BaseDetran:
    """Simulação das fontes de dados que o app consulta (inferido, não observado)."""

    def __init__(self) -> None:
        self.debitos = {"98765432100": ["IPVA 2026: R$ 1.250,00", "Multa: R$ 195,23"]}
        self.restricoes = {"98765432100": ["Restrição judicial (RENAJUD)"]}
        self.financiamentos = {"55555555555": ["Alienação fiduciária - Banco X"]}

@dataclass
class ResultadoConsulta:
    tipo: str
    itens: list[str] = field(default_factory=list)

    @property
    def limpo(self) -> bool:
        return not self.itens

    def __str__(self) -> str:
        if self.limpo:
            return f"[{self.tipo}] nada consta"
        return f"[{self.tipo}] " + "; ".join(self.itens)


# Product
class Consulta(ABC):
    def __init__(self, base: BaseDetran) -> None:
        self._base = base

    @abstractmethod
    def executar(self, renavam: str) -> ResultadoConsulta: ...


# Concrete Products
class ConsultaDebitos(Consulta):
    def executar(self, renavam: str) -> ResultadoConsulta:
        return ResultadoConsulta("Débitos", self._base.debitos.get(renavam, []))


class ConsultaRestricoes(Consulta):
    def executar(self, renavam: str) -> ResultadoConsulta:
        return ResultadoConsulta("Restrições", self._base.restricoes.get(renavam, []))


class ConsultaFinanciamentos(Consulta):
    def executar(self, renavam: str) -> ResultadoConsulta:
        return ResultadoConsulta("Financiamentos", self._base.financiamentos.get(renavam, []))


class ConsultaNadaConsta(Consulta):
    def executar(self, renavam: str) -> ResultadoConsulta:
        itens = (
            self._base.debitos.get(renavam, [])
            + self._base.restricoes.get(renavam, [])
            + self._base.financiamentos.get(renavam, [])
        )
        return ResultadoConsulta("Nada Consta", itens)

# Creator
class ConsultaCreator(ABC):
    def __init__(self, base: BaseDetran) -> None:
        self._base = base

    @abstractmethod
    def criar_consulta(self) -> Consulta:
        """Factory Method: subclasses decidem qual Consulta instanciar."""

    def consultar(self, renavam: str) -> ResultadoConsulta:
        consulta = self.criar_consulta()
            return consulta.executar(renavam)


# Concrete Creators
class DebitosCreator(ConsultaCreator):
    def criar_consulta(self) -> Consulta:
        return ConsultaDebitos(self._base)


class RestricoesCreator(ConsultaCreator):
    def criar_consulta(self) -> Consulta:
        return ConsultaRestricoes(self._base)


class FinanciamentosCreator(ConsultaCreator):
    def criar_consulta(self) -> Consulta:
        return ConsultaFinanciamentos(self._base)


class NadaConstaCreator(ConsultaCreator):
    def criar_consulta(self) -> Consulta:
        return ConsultaNadaConsta(self._base)


# Testando

if __name__ == "__main__":
    base = BaseDetran()
    renavam = "98765432100"  # tem debitos e restrição

    print("\n== FACTORY METHOD ==")
    for creator in (DebitosCreator(base), RestricoesCreator(base),
                    FinanciamentosCreator(base), NadaConstaCreator(base)):
        print(creator.consultar(renavam))

```

##### Participantes do padrão no código

**Product — `Consulta`:** classe abstrata que define a interface comum de todas as consultas. Seu método abstrato `executar(renavam)` obriga cada tipo de consulta a implementá-lo, e é por essa abstração que o resto do sistema enxerga qualquer consulta.

**Concrete Products — `ConsultaDebitos`, `ConsultaRestricoes`, `ConsultaFinanciamentos`, `ConsultaNadaConsta`:** cada uma herda de `Consulta` e implementa `executar` buscando os dados na fonte correspondente da `BaseDetran`. A `ConsultaNadaConsta` reúne as três fontes, e o resultado é considerado limpo quando nenhuma delas retorna pendência.

**Creator — `ConsultaCreator`:** declara o Factory Method abstrato `criar_consulta()` e implementa `consultar(renavam)`. Este último chama `criar_consulta()` e executa o produto retornado, sem nunca referenciar uma classe concreta. É aqui que a decisão de criação fica isolada do uso.

**Concrete Creators — `DebitosCreator`, `RestricoesCreator`, `FinanciamentosCreator`, `NadaConstaCreator`:** sobrescrevem `criar_consulta()` e retornam a consulta concreta correspondente, injetando a `BaseDetran`. Cada tipo novo de consulta exige apenas um par produto-creator.

**Classes de apoio (fora do padrão):** `ResultadoConsulta` padroniza o retorno, com a propriedade `limpo` indicando se há pendências, e `BaseDetran` simula as fontes de dados, cujo conteúdo é uma suposição, já que não há acesso ao backend real.

**Cliente:** o bloco `if __name__ == "__main__"` instancia os quatro Creators e chama `consultar(renavam)` em cada um. Para trocar o tipo de consulta, basta trocar o Creator, sem alterar o restante do código.

*resultado:* a IA apontou que o Singleton estava bem aplicado, mas que o trecho que eu havia chamado de Factory Method **não era** o padrão. A escolha entre `Carro` e `Moto` acontecia por um `if` dentro do método `build()` do Builder, o que caracteriza uma *Simple Factory* (que não é um padrão GoF). Não havia um **Creator** nem subclasses sobrescrevendo um método de criação, que são os elementos que definem o Factory Method.

**Validação e decisão:** Conferi a afirmação com o material da disciplina e confirmei que os participantes Creator e Concrete Creator realmente estavam ausentes. Concordei com a crítica e, em vez de manter o código misturado, decidi aplicar o Factory Method ao fluxo de **Consulta de Veículo**, em que existem quatro variações (débitos, restrições, financiamentos e nada consta) com a mesma interface.
