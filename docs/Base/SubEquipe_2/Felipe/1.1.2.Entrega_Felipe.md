### GoF Estrutural

#### Contexto (Problema)

No fluxo de **Identificação de Condutor**, esta proposta representa uma pessoa requerente que informa o auto de infração, identifica o condutor indicado e associa referências aos anexos da solicitação. O envio deve devolver uma confirmação de recebimento que possa ser apresentada ao usuário. A avaliação administrativa da indicação fica fora desse recorte.

O cliente da aplicação trabalha com um objeto `PedidoIndicacao` e espera executar `protocolar(pedido)`, recebendo um `ReciboProtocolo`. Para estudar a integração, foi criado um serviço fictício com outra assinatura: `registrar_indicacao(dados_legados)`. Esse serviço espera campos como `numero_auto`, `id_solicitante` e `id_indicado`, e devolve `numero_protocolo` e `status_envio`.

O serviço é uma hipótese didática em memória. Seus campos e seu comportamento não descrevem uma API observada do Detran-DF. A classe `TelaIndicacao` representa o cliente do padrão no terminal; este protótipo não implementa uma interface gráfica móvel.

Sem um adaptador, cada cliente que enviasse a solicitação precisaria conhecer os detalhes do serviço. Um trecho de integração direta seria:

```python
# Exemplo do acoplamento que se deseja evitar no cliente.
resposta = legado.registrar_indicacao({
    "numero_auto": pedido.auto,
    "id_solicitante": pedido.requerente_id,
    "id_indicado": pedido.condutor_id,
    "documentos": list(pedido.anexos),
})
numero = resposta["numero_protocolo"]
status = resposta["status_envio"]
```

Essa abordagem traz três dificuldades:

- **Acoplamento:** a tela precisa conhecer nomes de campos e métodos específicos do serviço.
- **Duplicação:** outras telas que enviem solicitações tendem a repetir a tradução e a interpretação da resposta.
- **Manutenção:** uma mudança no contrato externo pode exigir alterações em vários clientes.

O **Adapter** converte a interface de um objeto para aquela esperada pelo cliente. Nesta aplicação, `AdaptadorProtocoloLegado` implementa o contrato `PortaProtocolo` e delega o registro ao `ServicoLegadoSimulado`. A tela continua chamando `protocolar(pedido)`; a tradução fica concentrada no adaptador. Trata-se de um **Adapter de objetos**, pois ele mantém uma referência ao serviço adaptado e usa composição (GAMMA et al., 1994).

Uma **Facade** teria como intenção simplificar o acesso a um subsistema; um **Decorator** acrescentaria comportamento preservando a interface. O Adapter foi escolhido porque o problema formulado é a incompatibilidade entre dois contratos. Se o serviço já implementasse diretamente `PortaProtocolo`, essa camada adicional seria dispensável.

| Participante do padrão | Classe ou interface | Responsabilidade |
|---|---|---|
| **Client** | `TelaIndicacao` | Envia a solicitação usando somente a interface esperada pela aplicação. |
| **Target** | `PortaProtocolo` | Define `protocolar(PedidoIndicacao) -> ReciboProtocolo`. |

`PedidoIndicacao` e `ReciboProtocolo` são objetos de dados que transportam a entrada e a saída. O estereótipo `dados` é uma legenda local do diagrama, sem representar um participante GoF adicional.

A realização tracejada entre adaptador e interface expressa a conformidade com o contrato. Em Python, `typing.Protocol` permite essa conformidade por tipagem estrutural: uma classe pode oferecer o método compatível sem herdar explicitamente de `PortaProtocolo`. As anotações auxiliam a análise estática; a validação da resposta em execução é feita explicitamente no adaptador ([documentação do Python](https://docs.python.org/3.12/library/typing.html#typing.Protocol)).

#### Implementação do diagrama em código

A implementação está em `codigo/indicacao_adapter.py`. Ela usa a biblioteca padrão do Python e dados fictícios. O código completo é:

```python
"""Protótipo de Adapter para a identificação de condutor.

Todo o serviço externo é simulado em memória. Nenhuma chamada ao Detran-DF é feita.
"""
from __future__ import annotations

from dataclasses import dataclass
from typing import Protocol


@dataclass(frozen=True)
class PedidoIndicacao:
    auto: str
    requerente_id: str
    condutor_id: str
    anexos: tuple[str, ...] = ()

    def __post_init__(self) -> None:
        if not all((self.auto.strip(), self.requerente_id.strip(), self.condutor_id.strip())):
            raise ValueError("Auto, requerente e condutor são obrigatórios")


@dataclass(frozen=True)
class ReciboProtocolo:
    numero: str
    situacao: str


class PortaProtocolo(Protocol):
    """Target esperado pelo cliente da proposta móvel."""

    def protocolar(self, pedido: PedidoIndicacao) -> ReciboProtocolo: ...


class TelaIndicacao:
    """Client: depende só do contrato estável PortaProtocolo."""

    def __init__(self, porta: PortaProtocolo) -> None:
        self._porta = porta

    def enviar(self, pedido: PedidoIndicacao) -> str:
        recibo = self._porta.protocolar(pedido)
        return f"Solicitação recebida: {recibo.numero} ({recibo.situacao})"


class ServicoLegadoSimulado:
    """Adaptee fictício com assinatura e campos incompatíveis."""

    def __init__(self, situacao_resposta: str = "RECEBIDO") -> None:
        self.situacao_resposta = situacao_resposta
        self.chamadas: list[dict[str, object]] = []

    def registrar_indicacao(self, dados_legados: dict[str, object]) -> dict[str, object]:
        self.chamadas.append(dados_legados)
        return {
            "numero_protocolo": f"SIM-{len(self.chamadas):03d}",
            "status_envio": self.situacao_resposta,
        }


class ErroIntegracao(ValueError):
    """Resposta incompatível ou rejeitada pelo contrato simulado."""


class AdaptadorProtocoloLegado:
    """Adapter: converte chamada e resposta, sem decidir mérito da indicação."""

    def __init__(self, legado: ServicoLegadoSimulado) -> None:
        self._legado = legado

    def protocolar(self, pedido: PedidoIndicacao) -> ReciboProtocolo:
        dados_legados = {
            "numero_auto": pedido.auto,
            "id_solicitante": pedido.requerente_id,
            "id_indicado": pedido.condutor_id,
            "documentos": list(pedido.anexos),
        }
        resposta = self._legado.registrar_indicacao(dados_legados)
        numero = resposta.get("numero_protocolo")
        situacao = resposta.get("status_envio")
        if not isinstance(numero, str) or not numero.strip():
            raise ErroIntegracao("Resposta sem número de protocolo")
        if situacao != "RECEBIDO":
            raise ErroIntegracao(f"Envio não confirmado: {situacao!r}")
        return ReciboProtocolo(numero=numero, situacao="RECEBIDA")
```

##### Explicação dos participantes

**Objetos de dados.** `PedidoIndicacao` reúne os três identificadores e as referências aos anexos. Seu `__post_init__` rejeita identificadores vazios. `ReciboProtocolo` representa a confirmação de recebimento. As duas classes usam `dataclass(frozen=True)` para impedir a reatribuição comum dos campos após a criação.

**Target — `PortaProtocolo`.** Declara a operação que o cliente conhece: `protocolar`. Esse contrato fornece um ponto estável para utilizar diferentes implementações de integração.

**Client — `TelaIndicacao`.** Recebe uma porta no construtor, chama `protocolar` e monta a mensagem com o recibo. A escolha do adaptador ocorre na montagem do programa de demonstração.

**Adaptee — `ServicoLegadoSimulado`.** Simula um componente com nomes de operação e de campos incompatíveis com os do cliente. O registro das chamadas permite verificar exatamente o que o adaptador enviou. O protocolo `SIM-001` é sequencial, fictício e restrito à instância em memória.

**Adapter — `AdaptadorProtocoloLegado`.** Mantém a referência ao serviço, converte o pedido em um dicionário, delega a chamada e traduz a resposta em `ReciboProtocolo`. Antes de devolver sucesso, exige um protocolo não vazio e o status `RECEBIDO`. `ErroIntegracao` representa a falha desse contrato.

| Informação da aplicação | Campo no serviço simulado | Conversão |
|---|---|---|
| `pedido.auto` | `numero_auto` | Preserva o identificador do auto. |
| `pedido.requerente_id` | `id_solicitante` | Preserva o identificador do requerente. |
| `pedido.condutor_id` | `id_indicado` | Preserva o identificador do condutor. |
| `pedido.anexos` | `documentos` | Converte a tupla em lista de referências. |
| `ReciboProtocolo.numero` | `numero_protocolo` | Exige texto não vazio na resposta. |
| `ReciboProtocolo.situacao` | `status_envio` | Converte `RECEBIDO` em `RECEBIDA`; outros valores geram erro. |

O adaptador valida o formato da confirmação. A existência real do auto, a autenticidade dos documentos, a autorização do requerente e a decisão sobre a indicação não são verificadas por este exemplo.

##### Testando o fluxo

O arquivo `codigo/demo.py` monta os objetos e executa o fluxo de Identificação de Condutor:

```python
"""Execute com: python -m codigo.demo"""
from .indicacao_adapter import (
    AdaptadorProtocoloLegado,
    PedidoIndicacao,
    ServicoLegadoSimulado,
    TelaIndicacao,
)


def main() -> None:
    legado = ServicoLegadoSimulado()
    porta = AdaptadorProtocoloLegado(legado)
    tela = TelaIndicacao(porta)
    pedido = PedidoIndicacao(
        auto="AUTO-EXEMPLO-01",
        requerente_id="PESSOA-A",
        condutor_id="PESSOA-B",
        anexos=("anexo-ficticio.pdf",),
    )

    print("1. Cliente chama PortaProtocolo.protocolar(pedido)")
    print("2. Adapter chama ServicoLegadoSimulado.registrar_indicacao(dados)")
    print(tela.enviar(pedido))
    dados = legado.chamadas[0]
    print(f"3. Traduzido: numero_auto={dados['numero_auto']}, id_indicado={dados['id_indicado']}")
    print(f"   documentos={dados['documentos']}")
    print("4. Recebimento confirmado; não significa deferimento")


if __name__ == "__main__":
    main()
```

##### Verificação da implementação

Os cinco testes em `tests/test_indicacao_adapter.py` verificam comportamentos observáveis do fluxo:

| Cenário | Resultado verificado |
|---|---|
| Tradução de entrada e saída | O serviço recebe os quatro campos esperados e o cliente apresenta `SIM-001 (RECEBIDA)`. |
| Substituição da implementação | Uma porta em memória funciona no mesmo cliente, sem alterar `TelaIndicacao`. |
| Serviço devolve `REJEITADO` | O adaptador lança `ErroIntegracao` e não produz recibo de sucesso. |
| Resposta sem número de protocolo | O adaptador lança `ErroIntegracao` com indicação do campo ausente. |
| Pedido com identificador vazio | `PedidoIndicacao` lança `ValueError` antes do envio. |

Esses testes verificam o contrato do protótipo. O teste com uma segunda implementação da porta evidencia o desacoplamento; os testes negativos impedem que uma resposta inválida seja apresentada como sucesso. O exemplo não inclui comunicação em rede ou persistência.

#### Exemplo de análise crítica do código e dos diagramas

A conferência da modelagem identificou que `PedidoIndicacao` estava marcado como `Product` na versão anterior do diagrama. Esse nome poderia confundir a leitura com os participantes de um padrão criacional. A revisão passou a identificá-lo como objeto de dados e manteve os quatro papéis do Adapter explicitamente associados às classes corretas. Também alinhou os atributos `_porta` e `_legado` aos nomes usados no código.

No código, a análise verificou se a tela realmente dependia da abstração. O teste `test_cliente_aceita_outra_implementacao_da_porta` utiliza uma porta em memória com a mesma operação e confirma que o cliente continua funcionando. Os testes de rejeição e de resposta sem protocolo verificam outra decisão: uma chamada ao serviço só pode gerar confirmação se o retorno atender ao contrato.
